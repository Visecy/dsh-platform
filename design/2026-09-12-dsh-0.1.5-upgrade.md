# DSH 0.1.2-rc.1 → 0.1.5-rc.1 升级报告

日期：2026-09-12
目标版本：`@deepseek-ai/dsh@0.1.5-rc.1`（npm `latest`，本地 CLI 同版本）
上一基线：`0.1.2-rc.1`（commit `2a40e2c`）
（npm 上还有 `0.1.5-rc.2`（`next` 标签）：其 `lib/**` 与 rc.1 **逐字节相同**，只有构建版本字符串不同，因此以 `latest` 的 rc.1 为准并精确锁版本。）

---

## 1. 结论摘要

1. **大部分 seam 没有变。** `dsh-settings`、`dsh-credentials`、`dsh-storage`、`dsh-storage-domain`、
   `dsh-host-directory-picker`、`dsh-api-workspace-controller`、`dsh-host-webserver`、
   `dsh-sandbox`、`dsh-invariants`、`dsh-util-*` 的 `lib/**` 在 0.1.5 与 0.1.2 **逐字节相同**，
   只有 package.json 版本号变化。这些包对应的平台实现（`user-domain`、`storage-db`、
   `platform-domain`、`workspace-picker`、`vendor/dsh-web-auth`）**无需改动**。
2. **两个硬 BLOCKER**：`ctx.fs.readByteRange`（0.1.5 新增抽象成员）未实现会让工作区文件查看/下载
   直接 `TypeError`；`ctx.sessionPersistence` 从 `PersistenceCoordinator/PersistenceBackend`
   改成 **handle 模型**，旧实现无法编译也无法运行（详见 §4）。
3. **一个已存在的部署级 BLOCKER（本次通过新加的导入冒烟才发现）**：profile 以
   `autoInstallPeers: false` 安装，而 `--dump-config` 不会 import 插件本体，因此
   `dsh-session` / `dsh-llm` / `dsh-scope` / `dsh-http-proxy` / `dsh-session-format-catalog`
   这几个**运行时 import** 的对等依赖此前根本没进镜像 —— `fs-k8s` 与
   `session-persistence-rdb` 在真实启动时会 `ERR_MODULE_NOT_FOUND`。已在 Dockerfile 补齐并加了
   构建期断言（§3.5）。
4. **两处与官方编译产物耦合的补丁仍然有效**：`scripts/patch-dsh.mjs` 的两个片段在 0.1.5 上
   逐字节命中；`vendor/dsh-web-auth` 的 webserver fork 因为上游包逐字节未变而无需重做。
   已加端到端冒烟（§6）。
5. 顺带修好了若干**真实缺陷**（不是本次升级引入的）：`sandbox-daemon` 根本无法通过 `pnpm build`
   的类型检查；`groupAlive` 在本环境永远返回 false（导致 kill 升级梯失效、pgid=-1 时会朝 PID 1
   发信号）；`Record` 局部类型遮蔽 TS 全局工具类型；`CollectReader` 坐标系错误导致每次流式
   bash 都被标记 `lossy: true`；`stat`/`lstat` 无法区分；大文件读整文件缓冲（OOM 风险）。

### 3.3 执行世界 seam

* `fs-k8s`：实现 `readByteRange`；`readBytes` 改为"读 `maxBytes+1` 再判断"，把 `FS_TOO_LARGE`

  `resolveExecutable` 改走 per-workspace endpoint（原先打到默认 endpoint，即错误的 pod）；
  env 墓碑以 `null` 过线；删除已不存在的 `pid` 成员；新增 dispose 钩子终止并等待所有存活句柄。
* `workspace-k8s`：`HostWorkspaceRegistry.create` 对非绝对路径给出可操作报错（0.1.5 会在任何 I/O

## 4. 顺带修好的真实缺陷

这些都不是 0.1.5 引入的，但都在本次改动路径上，且都会造成实际故障：

| 缺陷 | 症状 | 修复 |
|---|---|---|
| `groupAlive` 用 `ps -eo pgid=` 解析 | 本环境每行 pgid 恒为 0 → 永远返回 false：`terminateGroup` 的 SIGKILL 升级梯失效；`waitForExit` 永远认为范围已空 | 改用 `process.kill(-pgid, 0)` 系统调用探测 |
| `terminateGroup(-1)` | `kill(-(-1))` = `kill(1)` → 朝容器 PID 1（通常是自己）发信号 | pgid ≤ 0 直接视为 no-op；`scan()` 跳过未发布 pgid 的记录 |
| `scan()` 异步覆盖 phase | 超时命令可能被 status() 抢先标成 `exited` | 同步发布 `killed` + `reason: timeout` |
| `interface Record` 遮蔽全局 `Record<K,V>` | `sandbox-daemon` 的 `tsc --noEmit` 失败（`Record` 不是泛型、缺 `groupDir`）→ `pnpm build` 红 | 重命名为 `CommandRecord`/`PtyRecord`；`groupDir` 设为可选并在 status 里守卫 |
| `sandbox-daemon` TS 版本 | devDependency `^5.5` 但 tsconfig 用了 5.7+ 的 `rewriteRelativeImportExtensions` | 升到 `^7.0.2`；`skipLibCheck` 消除 vitest/vite 与 @types/node 的 FSWatcher 冲突 |
| `CollectReader.readFrom` 坐标系 | `nextOffset` 返回的是**保留窗口长度**而不是全流偏移，`lossy` 对每次增量读都为 true → 每个流式 bash 调用在 UI 上都显示"已截断" | 按参考实现改为 `total`/`windowStart` 全流坐标；结算时 `close()` 封口 spill 文件 |
| `fs-k8s` `stat`/`lstat` 不分 | 符号链接一律报 `other`，无法在跟随前拒绝路径本身 | 见 §3.3 |
| `storage-db` 每次都 `ensureSchema()` | 每个 unit open 都重跑 DDL | 按 backend 实例缓存 promise |
| `docker/.../Dockerfile` 头注释 | 描述了一个两个版本都不存在的 "privileged-method unlock patch" | 改写为实际的信任钉子说明 |

## 5. session-persistence-rdb 重写

**为什么必须重写**：0.1.5 删除了整个 `PersistenceCoordinator`/`PersistenceBackend` 接缝，
`ctx.sessionPersistence` 变成 handle 模型：

```ts
abstract create(header, options?): Promise<SessionHandle>
abstract open(id, 'read' | 'write', options?): Promise<SessionHandle>
abstract flush(): Promise<void>
abstract stat(id, options?): Promise<SessionPersistenceSnapshot | undefined>
abstract list(options?): Promise<readonly SessionPersistenceSnapshot[]>
// SessionHandle: id/header/inheritedEventCount/access
//   read(offset?, length?, {signal}) -> {eventState, events}
//   append(events, {signal}) / flush({signal}) / close()
```

同时 `SESSION_FORMAT_VERSION` 从 0 跳到 3，读路径**硬拒绝**旧版本，因此现网所有
`sessions.sqlite` 在迁移落地前都会抛 `SessionFormatUnsupportedError`。

实现要点（`packages/session-persistence-rdb/src/`）：

* 保留原有存储层（drizzle + SQLite/PostgreSQL、`t_sessions`/`t_events`、`write-guard`、实体与
  DDL 适配器），把服务面替换为 handle；新增 `handle.ts`（每会话句柄：单句柄串行队列、单调读、
  诚实的 `eventState: 'detached'`、caller-owned 数组、真正的 flush 屏障、幂等且不可取消的
  `close`）、`tracker.ts`（进程内单写者注册、create 后未落盘会话对 `stat`/`list`/`open` 可见、
  `session/event`→缓冲 / `session/flush`→drain+flush / `session/disposed`→close 的实时路由、
  收尾时先关句柄再关库）、`migrate.ts`（旧日志 v0→v3 迁移）。
* **迁移采用官方 `sessionFormatCatalog`**：读路径用 RDB 自己的列合成 released 物理记录
  （header 记录 + 每事件一行 `{type, seq, time, data, …surface}`），再走
  `createRestore(header, {recovery:'strict', validation:'transformed'}).decodeRow/finish` 得到
  v3 工件；系统提示提升到 surface 节点 0、`assistant/chunk`→`assistant/attempt` 的 stream 内嵌、
  PTC 改名、`start/end`→`startSeq/endSeq` 全部由 catalog 完成，不手写。
* 两类存量数据显式分开处理：**A. 身份日志**（`f_sequence == f_original_seq`，即 0.1.2 时代与当前）
  原样过链；**B. rc.2 时代稠密重编号日志**（`f_original_seq != f_sequence`）先做一次引用重映射
  （`sourceEventSeqs`、surface 区间、`shadowedRange`/`shadowedSeqs`、标题 `messageSeqs`、
  `command/done.sourceEventSeq`、`f_seed_length`），再走同一条链。
* **写打开时原地重写**：v3 追加行不能与 v0 行共存，因此 `open(id,'write')` 在一个事务里把日志
  重写成 v3 后再授予所有权（`open(id,'read')` 永不改写）。
* 无法迁移的形状**响亮拒绝**（`SessionFormatUnsupportedError` 并带上数据库路径）：已废弃词表
  （`request/header-delta`、`mode/set`、`header.system` fallback…）、首个 `step/start` 之前出现
  surface 事件（上游拒绝重排时序）、比 3 更新的 `f_version`、以及提交区内部的 seq 空洞。
* `log.ts` 的 `{op:'replace', start, end}` 改为 `startSeq/endSeq`（这是**静默数据损坏**级别的
  问题：旧形状的 surface op 读回来会被判为非法 marker）、迁移后的 header 呈现 `version: 3`。
* 崩溃修复只剩"写路径在首次 append 前截断残尾"——closers 的插入现在是 agent loop 的职责。
* 错误词表改用官方类（`SessionAlreadyExistsError`/`SessionAlreadyOwnedError`/
  `SessionReadOnlyError`/`SessionHandleClosedError`…），`WriteGuard` 保留为**跨进程**持久头分歧
  检测（其拒绝现在是 `WriterDivergenceError extends SessionOwnershipLostError`）。

测试：原 `coordinator-contract.ts`（1812 行）针对已删除的 coordinator，已用
`testing/agent-loop.ts` 替换为针对真实 agent-loop 协议（`open(id,'write')` → `read(0)` → closers
→ `append` → `sessions.prepare({eventState})`）的等价套件，并补了迁移/拒绝用例；
fixture 中 `assistant/message` 补 `stream: []`、`assistant/chunk` 改 `assistant/attempt`。

## 7. 未做 / 建议的后续优化

按性价比排序：

1. **`resolve` 的稳定身份**：seam 要求 `resolve` 跟随符号链接产出稳定 `targetKey`，
   当前用原始 pod 路径，同一文件两种拼写会得到两个身份（影响观测策略的重复读）。
   需要给 daemon 加 `realpath` 语义。
2. **`user-domain` 是死代码**：`src/index.ts` 是 0 字节，没有任何 profile 行插入它，
   Dockerfile 也不装；per-user settings/credentials 实际上并不存在（当前是全进程共享的
   `dsh-settings-file` + `dsh-credentials-local`）。若要接线，同时要修两个真实 bug：
   `providers.ts` 的 `load()` 读环境用户而基类只缓存第一份文档（跨用户读泄漏），
   以及从不调用 `notifyUpdated`/`notifyRecordUpdated`（Models 页永远不刷新）。
3. **`sourceEventSeqs`/`stat` 缓存**：0.1.5 的 `stat()` 对"已 create 未落盘"的会话必须返回
   内存 revision —— 当前靠 tracker 的内存快照，值得在实现里明确断言。
4. **`daemon-protocol` 包是 0 字节且无人引用**，真正的协议在 `sandbox-daemon/src/protocol.ts`；
   要么删包、要么把类型收敛过去。
5. **`fs-k8s` 的其它边角**：`editText` 读完后重新 stat 做 CAS（丢失更新窗口）、
   `streamText` 先整文件读再一次 yield、`readBytes` 已修。
6. **`open-in-app`/`ui-open-in-app`** 在容器里没有意义（会经 subprocess-k8s 去 pod 里
   尝试拉起宿主应用），可以在 web profile 里 disable；本次保守保留，未改变现有行为。
7. **`subprocess-k8s` 的 ripgrep 翻译**目前按 `basename(argv[0]) === 'rg'` 硬编码，
   0.1.5 的 `dsh-tool-fs-search` 仍传宿主机绝对路径，逻辑必须保留；更稳的做法是把任何
   pod 内不可见的绝对 `argv[0]` 都经 `resolveExecutable(basename)` 翻译。
8. **`git` 里跟踪了 `packages/*/dist/index.js`**（`.gitignore` 写了但文件已入库），
   构建产物入库容易与源码漂移，建议 `git rm --cached`。

## 8. 风险与未验证项

* **没有可用的 PostgreSQL**：两个 profile 的 `storage-db`/`platform-domain`/`session-persistence-rdb`
  都配成 postgres，因此这里只验证到"配置可组合 + 插件可导入"，**没有真正启动过带 PG 的完整控制面**。
  PG 相关测试在无 PG 时跳过（`TEST_PG_URL` 门控，共 23 例）。RDB 的原始存储层事务原语在
  SQLite/PG 间共享，但"残尾 / released-v0 / 稠密重编号"这些构造性用例只在 SQLite 上跑过；
  建议在 CI 或本地 `TEST_PG_URL=… pnpm test` 补跑。
* **没有 k8s 集群**：`workspace-k8s` 的真实 pod 生命周期未跑通，只用 in-process daemon
  验证了 fs/subprocess 两个 seam 的实际语义。
* **浏览器端没有实机验证**：vendored browser 的 14 个 anchor 是静态验证（补丁命中 + 语法检查），
  以及 `layout` 注入的存在性核对；真实挂载仍建议按原流程用 CDP 过一遍。
* **rc.2 时代的旧库没有真实样本**：迁移里"稠密重编号"分支的形状是从旧 coordinator 的重映射代码
  与 released codec 反推的（有测试覆盖但无真实数据）；如果首批升级的实例里存在**首个 surface
  事件早于首个 `step/start`** 的会话，会被 `SessionFormatUnsupportedError` 拒绝（这是上游
  format chain 拒绝重排时序的刻意行为），需要单独手写迁移。
* **读取成本**：迁移链是单趟的，因此 handle 的读是**整日志解码**；`read(lastSeq, 1)`
  （`dsh-message-feedback` 用到）会重新解码整条日志。正确但 O(log)/次，后续可加按 revision
  的记忆化。
* **原地重写会留下孤儿 `t_events` 行**（只删桥接行），长期有磁盘增长；需要一个 vacuum/清扫步骤。
* **`agentPreset` 仍然丢失**（`t_sessions` 没有该列，加列要 `SCHEMA_VERSION` 自增并拒绝所有现存库，
  与本次升级目标相反）；这是升级前就存在的数据丢失缺口。
* `resolveExecutable` 的 `env` 覆盖与"裸名字用 pod PATH"语义尚未在 daemon 侧实现；
  带 workspace 路径的命令现在会路由到对应 pod，其余仍走默认 endpoint。
* `dsh-settings`/`dsh-credentials` 等"逐字节相同"的结论来自对同一版本 tarball 与本地安装的
  `diff -r`，不含未发布的源码分支。
* **`0.1.5-rc.2` 已发布**（npm `next`）：其 `lib/**` 与 rc.1 逐字节相同，本次刻意锁 rc.1
  （`latest` + 镜像 `DSH_VERSION`）。等 `0.1.5` 正式版发布时需要重跑本报告 §3.2 的三处复核
  与 §6 的验证矩阵。

## 9. 补丁面清单：现在还有哪些是 patch/fork，能否改走官方扩展点

### 9.1 清单（三处，全部是"改官方产物"）

| # | 位置 | 形式 | 内容 |
|---|---|---|---|
| P1 | `scripts/patch-dsh.mjs` → `dsh-client-connection/lib/client.js` | 编译产物精确字符串替换 | 浏览器 `isLoopback` 固定为 `true` |
| P2 | `scripts/patch-dsh.mjs` → `dsh-client-connection/lib/index.js` | 编译产物精确字符串替换 | `isAuthenticated()` 直接 `return true`（旁路 launch-token cookie 层） |
| F1 | `vendor/dsh-web-auth/lib/webserver.js` | **整文件 fork**（官方 `dsh-host-webserver` + `registerGate` 扩展） | 请求/升级在路由匹配**之前**过闸门 |
| V1 | `scripts/vendor-workspace-browser.mjs` → `vendored-workspace.ts` | 浏览器 bundle 上 14 处手术 | 工作区行的阶段点 / 唤醒-休眠-清理菜单 |

（`docker/profiles/*.cordis.patch.yml` 的 disable/insert 是官方配置层机制，不算 patch。）

### 9.2 P1 可以彻底去掉 —— 官方有类型化的 transport hook

上游 `ClientTransportHooks`（`dsh-client-connection/lib/types/client/index.d.ts`）里
`ownsHost?: boolean` 的文档原文：*"The transport owner declares the page owns the Host outright…
`ctx.connection.isLoopback` then reports the privileged surface reachable regardless of the page
authority."* 浏览器半边读的就是 `globalThis.__DSH_TRANSPORT__`，官方前端
（`dsh-web-frontend/dist/assets/index-*.js`）启动时也读同一个全局。

**替代做法**：平台宿主插件监听 `webserver/index-inject`，push 一行
`{ kind: 'global', name: '__DSH_TRANSPORT__', value: { ownsHost: true } }` —— 这正是上游自己注入
`__DSH_CONNECTION_RECOVERY__` 用的同一机制 —— 不必再改 `lib/client.js`。

**已验证**（`scripts/smoke-official-integration.mjs`，跑在**未打补丁**的 0.1.5 产物上）：
`transport?.ownsHost === true` 命中 → 表达式为真；不注入则为假；注入的全局出现在
`__DSH_BOOT_READY__` 之前。

**代价**：语义上是"页面独占 Host"，我们的真实理由是"OIDC 闸门已经认证过每个请求"，属于对 hook
语义的借用；但它有类型、有文档、有官方消费者，比改编译产物稳。

### 9.3 P2 可以改成"满足"而不是"旁路" —— 但收益是名义上的

上游暴露了两个公开方法：`ctx.connection.authenticatedUrl(baseUrl)`（*"Add this process's launch
token to the clean application URL"*）与 `ctx.connection.authorizeIndex(req, res)`（有效根 token →
铸造签名 cookie + 303 回干净 `/`）。所以 OIDC 闸门可以在用户登录后，把浏览器**重定向一次**到
`https://<public>/?token=<processToken>`，让官方 cookie 层自己完成握手；此后 `isAuthenticated()`
原生返回 true，不再需要 P2。

**已验证**（同一脚本，未打补丁产物）：无 cookie 的 `/api` → 401；`/` 在握手前 → 401；
`authenticatedUrl()` 产出 `?token=…`；带 token 的 `/` → **303 + Set-Cookie**；带 cookie 的 `/api`
→ 不再是 401；错误 token → 401；拿 cookie 也不能绕过 Host/Origin 围栏（陌生 Host → 403）。

**但是** —— 这是**多用户**部署，而 launch token 是**进程级**的：闸门要把它交给每一个已登录用户，
token 就落进浏览器 URL/历史/日志，等于进程内公开。"满足"这道检查因此不带来真实的额外安全性。

所以：
* 目标是"少一处 patch" → 采用 9.3（行为等价，去掉 P2）；
* 目标是"纵深防御" → 保持 P2 现状更诚实：真正的边界是 OIDC 闸门（按用户），DSH 的 cookie 层是
  进程级、无法表达"哪个用户"，把它打开并不会拦住任何人。

### 9.4 F1 没有官方中间件钩子，但可以自动发现漂移

0.1.5 的 `dsh-host-webserver` 公开面只有 `register`（exact/prefix）、`registerUpgrade`、
`registerFallback`、`renderIndex`/index-inject tap —— **没有**前置请求钩子。闸门必须在路由匹配
**之前**生效（否则静态 fallback 与其它插件路由都会漏），而路由处理器"拥有响应、无法放行到下一条"，
所以 fork 目前是唯一能保持"认证在进程内"的方案。替代只有两条且都不划算：退回 sidecar 反向代理
（架构改动），或把 fork 换成对官方文件的精确字符串补丁（同样是改编译产物，还失去可读源码）。

能做的改进是**把静默漂移变成构建失败**：`scripts/check-webserver-fork.mjs` 断言"官方文件的每一行
都仍存在于 fork 中"（fork 只新增行 + 改写 1 行 import，所以该不变量成立）。已接入 Dockerfile 与
`scripts/harness-profile.sh`；已用"改一行官方代码"的反例验证它会报错。

### 9.5 V1 官方没有替代，但可以降级成产品选择

官方 `dsh-client-ui-workspace` 的 client bundle **只导出 `apply`/`inject`**，组件不外露；
`sidebar.workspaces` 只提供一个 Children 洞（`sidebar.workspaces.directoryFlow`），
**没有行级装饰/徽标槽**。所以"在官方工作区行上显示 k8s 阶段 + 加唤醒/休眠/清理菜单"无法用组合
实现，vendoring 是当前唯一办法。

可行的替代是**改产品形态**（不是改实现）：0.1.5 新增了 keyed `main` 面板 + `sidebar.panellist`
图标行，可以把"工作区状态/生命周期"做成一个一等面板，从而完全去掉 vendored browser（代价是失去
侧栏行内的状态点）。另一条路是向上游提一个行级 badge 槽位。

### 9.6 结论

| 项 | 建议 | 依据 |
|---|---|---|
| P1 | **改走官方 `__DSH_TRANSPORT__` hook** | 零语义损失，去掉一处编译产物补丁，已验证 |
| P2 | 二者皆可：去掉 patch（9.3）或保留现状 | 安全性等价（进程级 token 对多用户无增量），只差维护点 |
| F1 | **保留 fork** + 新增漂移守卫 | 上游无前置钩子；守卫把风险变成构建失败 |
| V1 | **保留 vendoring** | 上游无行级槽位；除非改产品形态或推动上游加槽 |

若采纳 P1+P2，`scripts/patch-dsh.mjs` 可整体删除，"改官方编译产物"的地方就只剩两份**带自动守卫的
副本**（webserver fork、ui-workspace bundle），不再有任何字符串补丁。

## 10. 登录与多用户：上游到底给了什么，我们该怎么做

### 10.1 一句话结论

**0.1.5 没有多用户支持，也没有任何"认证接入点"可以替换掉这套 token 登录。**上游是彻头彻尾的
单用户/本机设计：没有任何 seam 携带"调用者是谁"，RPC 处理器签名里连 request 都没有。
能替换 token 方案的地方只有一个 —— **webserver 这个 service 座位本身**（也就是我们现在 fork
的东西），或者把进程放到反向代理后面。

### 10.2 上游身份面：有证据的"没有"

| 搜什么 | 结果 |
|---|---|
| 全部 `interface Context` 增强里的服务名 | 没有任何 `principal` / `tenant` / `userId` / `accountId`（整个类型面 0 命中） |
| `dsh-anonymous-user-id` | 文档原文：*"**Per-harness-home** anonymous user id… every process sharing one `$DSH_HOME` reports the same id"* —— 一个 Harness home 一个身份，用于遥测/反馈关联 |
| `ctx.settings` | *"Providers store **one raw document** of per-namespace sections"* —— 单文档 |
| `ctx.credentials` | 键是 `credentialKey(scope, id)`，scope = *"the owning plugin's registered name"* —— 没有用户维度 |
| `dsh web --help` | 只有 `--host` / `--port` / `--no-open` / `--trusted-host`，没有 login/user/auth |
| RPC 处理器调用点 | `await handler(endpoint, message.payload, request.signal)` —— **没有 caller、没有 per-request ctx** |
| `AsyncLocalStorage` 全仓库 | 只有 `dsh-agent` 的"发起 agent"归属追踪，不是请求/用户上下文 |
| `dsh-authorization` | 文档原文：*"obtaining a credential nobody can supply from configuration alone… open this page, paste that code, pick an account"* —— 是**拿 LLM 供应商凭据**（device flow），不是认证调用者 |

也就是说：会话、设置、凭据、存储、遥测、UI 全都是"一个进程 = 一个用户"的假设。

### 10.3 token 登录的意图（读官方文档的原文）

`dsh-client-connection` 的 `browser-auth` 是**本机启动便利**，不是认证系统：
进程启动时生成一个 launch token，把 `http://127.0.0.1:3080/?token=…` 打印出来/自动打开浏览器，
浏览器用它换一个绑定 authority 的签名 cookie；此后 `/api` 与 index 都要求这个 cookie。
同一份文档还写明 `dsh-host-frontend-static`：*"**Non-index assets stay public.**"* ——
**上游根本没打算把 HTTP 层当安全边界**。

所以远程/多用户部署必然要在进程外或进程内的 HTTP 层自己加认证，这不是我们把它用歪了，
而是上游没提供这个层。

### 10.4 请求路径上到底有哪些扩展点（能否做认证闸门）

| 扩展点 | 能拦什么 | 能不能当认证闸门 |
|---|---|---|
| `webServer.register({kind:'exact'\|'prefix'})` | 只有你自己声明的路径；handler 拥有响应、**无法放行到下一条** | ✗ |
| 同上但注册 `prefix: '/'` | 前缀**最长优先**，`/` 会被 `/api`、`/plugins` 压过；它能盖住 fallback，但没有任何 API 能再调回 fallback | ✗（会截断整站） |
| `webServer.registerUpgrade` | 只有你声明的 upgrade 路径 | ✗ |
| `webServer.registerFallback` | fallback 座位（唯一占用者） | ✗（只覆盖未被命名路由认领的请求） |
| `webServer.tapIndex` / `webserver/index-inject` | 只改 index 的 HTML | ✗ |
| **`webServer` service 座位本身** | 全部请求（因为你就是那层 HTTP 载体） | ✓ **唯一真正的接入点** |
| `ctx.connection.requestRejection` | 它自己的围栏+cookie 模型 | ✗（是判定函数，不是钩子） |
| `ctx.connection.authorizeIndex` | 只有 index；静态资源按设计公开 | ✗ |
| `ctx.connection.rpc.intercept` / `fetch.register` | `/api` 内部的 RPC/Fetch（**在**官方信任策略之后） | ✗（认证）；✓（有身份后做鉴权） |
| `dsh-host-frontend-static` | 配置只有 `distIndex`，内部直接调 `authorizeIndex` | ✗ |

官方 `WebServer` 的 `server` / `match` / `exact` / `prefixes` / `fallback` 全是 **private**，
没有 protected dispatch 可覆写 —— 子类包一层也拦不到，除非自己重写整个插件（= 我们现在的 fork）。

**结论**：上游没有中间件钩子，"进程内认证"只能靠 fork webserver 座位；另一条路是在进程前放反向代理。
两者都不是"接一个官方集成点"，而是"自己成为/自建那一层"。

### 10.5 顺带修掉的一个实盘问题：launch token 被打进容器日志

`dsh-web-app` 的 `web-runtime` 行默认 `printUrl: true`、`openBrowser` 跟随 CLI（容器里没传
`--no-open`，所以也是 true）。启动时它会执行：

```js
if (config.printUrl) console.log(`dsh web: ${authenticatedUrl}${…}`)   // 带 ?token=<launchToken>
internals.openBrowser(authenticatedUrl)                                 // 容器里必然失败并再打一条错误
```

后果：**进程级认证密钥进了 pod 日志**（任何能看日志的人都能铸一个 DSH cookie），并且每次启动都
打一条无意义的浏览器启动失败。已在 `docker/profiles/web.cordis.patch.yml` 里按官方配置改掉：

```yaml
- id: web-runtime
  name: '@deepseek-ai/dsh-web-app'
  inject: [webStartup]
  config:
    openBrowser: false
    printUrl: false
    surfaceContext: true
    trustedHosts: !!js ctx.webStartup.trustedHosts
```

（若将来采纳 §9.3 的"满足 token"方案，这一步更是必须的：那时日志里的 token 就真的能换 cookie 了。
需要 tokenized URL 的进程内消费者可以直接调 `ctx.connection.authenticatedUrl(origin)`。）

### 10.6 替代方案（按推荐度）

1. **向上游提一个 gate 座位（最值得做）**。我们的 fork 里 `registerGate` 的实现只有约 30 行
   （一个座位字段 + 路由匹配前调用 + upgrade 分发前调用 + raw-socket 拒绝适配器）。如果上游接受，
   fork 直接删除，`auth-oidc` 改成注册 gate —— 这是唯一能把 F1 彻底消掉的路径，且对上游是纯增量。
2. **保留 fork**（现状）+ `check-webserver-fork.mjs` 漂移守卫。在 1 落地前这是最稳的。
3. **把 token 层从"旁路"改成"满足"**（§9.3，已验证）：去掉 P2，但仍然需要 fork 做 OIDC 闸门，
   所以它只减少一处补丁，不改变架构。多用户下安全收益为 0（进程级 token 人人可得）。
4. **进程前反向代理**：认证完全移出 DSH（oauth2-proxy 之类），DSH 只监听内网。
   问题在于 DSH 仍会拒绝没有官方 cookie 的浏览器，于是代理还得替浏览器完成官方 token 交换 ——
   而 token 只在进程内（`ctx.connection.authenticatedUrl()`），§10.5 之后连 stdout 都不再打印。
   这条路会变成"代理 + 平台插件把 token 交给代理"，组件更多、密钥路径更长。不推荐。
5. **不要**尝试用 `ctx.authorization` 当登录缝：它是 LLM 凭据获取流程，没有请求拦截能力，
   语义也完全不对。

### 10.7 多用户：平台自己的真实状态（比上游问题更紧迫）

上游没有多用户，那么"多用户"完全是平台自己的责任。目前的实际情况是
**认证有了，隔离基本没有**：

| 能力 | 现状 | 证据 |
|---|---|---|
| 用户认证 | ✅ OIDC 闸门（网关 + 会话 cookie） | `packages/auth-oidc` |
| 身份下传 | ⚠️ 有缝但没人用 | `plugin.ts:131` `ctx.provide('dshAuth', { currentUser })`；全仓库**零消费者** |
| 角色 | ⚠️ 算了但没人查 | `index.ts:103` 计算 `['user','admin']`；`rbac` 包 0 字节 |
| 每用户设置/凭据 | ❌ **未接线** | `user-domain/src/index.ts` 0 字节；没有任何 profile 行插入 `@vicecy/dsh-user-domain`；镜像也不装 → 实际用的是进程级 `dsh-settings-file` + `dsh-credentials-local` |
| 会话可见性 | ❌ 全局共享 | 会话列表来自官方 `ctx.workspaceRegistry` / `sessionPersistence.list()`，无用户维度 |
| 执行隔离 | ✅ 每工作区一个 pod/PVC | `workspace-k8s`（隔离的是执行环境，不是"谁看得见") |
| 每用户工作区归属 | ❌ 无 | `workspaceRegistry` 是进程级注册表 |

也就是说：**今天任何通过 OIDC 登录的人，能看到并操作所有人的会话与工作区，共享同一份模型凭据**。
`platform-domain` 的 schema 里已经有 `userId` 字段（settings/credentials 两个域），
`user-domain` 的 provider 代码也写好了（`providers.ts` 的 `currentUserId()`），但整条链没有插上。

### 10.8 要做真多用户，路该怎么走

关键约束：**cordis 服务是进程级的，RPC 调用不带调用者身份，也没有请求级上下文**（见 10.2）。
所以"当前用户"不能靠传输层自动获得，只能由平台自己绑定到一个可控的键上 —— 最自然的键是
**session**（长生命周期的 agent 运行以 session 为单位，而 HTTP 请求在运行开始后就消失了）。

建议顺序：

1. **先补可见性（安全底线）**：在平台自己的 API/UI 边界按用户过滤会话与工作区列表。
   官方 `sessionPersistence.list()` / `workspaceRegistry.list()` 是进程级且无用户维度，
   所以过滤必须发生在平台层（`workspace-k8s` 已经拥有 `/workspaces/api/*` 与侧栏 UI，位置合适），
   并把 sessionId→userId 的映射落库（`platform-domain` 已有 `userId` 字段的域，可直接用）。
2. **再接线每用户设置/凭据**：把 `user-domain` 接上（插 profile 行 + 禁掉进程级的
   `settings`/`credentials` 行 + 镜像安装），并修掉它现有的两个真实缺陷
   （基类缓存第一份文档导致跨用户读泄漏；从不调用 `notifyUpdated`/`notifyRecordUpdated`）。
   难点是"provider 怎么知道当前是哪个用户"：provider 是进程级服务，必须由平台在**发起该次运行的
   session 上下文**里解析用户 —— 可行做法是平台维护 `sessionId → userId` 并在自己的入口
   （创建会话/提交 prompt 的 RPC handler）把用户写进运行时状态，provider 从"当前运行的 session"
   反查；不要依赖 ALS 跨后台任务传播（定时任务、goal round 会丢上下文）。
3. **最后补授权**：`rbac` 的空壳要落地（谁能看/改哪些工作区、只读分享、admin 角色生效）。
   `ctx.connection.rpc.intercept` 可以作为"有身份之后"的统一鉴权点（它在官方信任策略之后运行），
   但它是 API 级的，静态资源与 index 仍由闸门兜底。
4. **顺带**：把 `dshAuth` 真正接上消费者（现在定义了没人用），并让 `adminGroups` 的 `roles` 生效。

一句话：**上游不会给你多用户；平台今天只做了一半（认证），另一半（授权 + 隔离）需要按上面的顺序补，
且必须在平台自己的边界上做，因为官方的列表/设置/凭据接缝都是进程级的。**

### 10.9 独立审计的补充证据与由此新增的运维事实

另跑了一遍穷举审计（240 个包、118 处 `interface Context` 增强 → 103 个服务名、85 个事件），
结论一致，并补出几条更有分量的原文与事实：

**官方文档自己划清界限（可直接引用）**
* `dsh-client-connection/README.md:39`：*"These checks defend DNS rebinding and cross-site browser
  requests; **they never establish identity**."*
* `dsh-connection` 的 `api-request-trust.d.ts:12-13`：*"**this fence is not an auth layer**"*
* `dsh-settings/README.md:90,149`：*"**single user layer** … one composition `base`, and one user
  document"*
* `dsh-anonymous-user-id/README.md:28`：*"**Do not use it to identify a user** or to join records
  across different homes"*
* `dsh-client-connection/README.md:68`：*"**There is no logout operation**"*；cookie 因为只服务
  loopback HTTP 而**故意不带 `Secure`**；`--host 0.0.0.0` 在启动时被直接拒绝，理由是
  *"it would expose **remote code execution** to the network; use 127.0.0.1 instead"*
  （`dsh-web-app/lib/startup.js:40`）
* 103 个 service、85 个 event **没有任何一个携带调用者身份**；唯一的 `user.id` 就是上面那个
  home 级匿名 id。

**对平台直接相关的三条**

1. **我们是刻意在官方威胁模型之外运行的**：官方拒绝 `0.0.0.0`（因为它把 HTTP 面视为等价于 RCE），
   而我们的 profile 直接在 webserver 行上写 `host: '0.0.0.0'`。这**不是**漏洞，但意味着
   **OIDC 闸门是唯一的安全边界**，它必须覆盖每一个路由 —— 见下一条。
2. **上游有两条路由完全没有信任检查**：`/plugins`（client-modules 的客户端 bundle）与
   `/plugins/events`（client-hmr 的 SSE），二者都不调用 `requestRejection`。官方 webserver 下
   它们对任何能连上端口的人开放。**我们的 fork 因为闸门在路由匹配之前，天然覆盖了它们**——
   已把它固化成断言（`smoke-web-trust.mjs`）：
   `a named /plugins route is reachable when authenticated`（200）与
   `the SAME named route is denied without a session`（401），同时验证 fallback 也 401、
   `/auth/login` 仍放行。以后任何"闸门只包了 fallback"的退化都会在冒烟里立刻暴露。
3. **多用户下最直观的泄漏点不是会话列表，而是审批/提问广播**：官方
   `broadcastRemoteEvent` 会把 approval / question 事件推给**所有已连接的浏览器**。
   在多用户部署里，A 的"是否允许执行这条命令"会弹到 B 的界面上。修可见性时这一条要一起处理
   （平台接管 `/api/remote.mux` 的订阅或在前端按 session 过滤）。

**平台已经补上的官方缺口**：官方"没有 logout"，而 `packages/auth-oidc` 注册了
`/auth/login`、`/auth/callback`、**`/auth/logout`** 三个路由（in-process 与 sidecar 两种形态都有），
所以这一条不需要额外工作。

**一个版本学细节**：官方 CLI 0.1.5-rc.1 的 `node_modules` 里那 230 个 `dsh-*` 包实际是
**0.1.5-rc.2**（因为上游自己也用 `^0.1.5-rc.1`）。本仓库把直接依赖精确锁到 `0.1.5-rc.1`
（`peerDependencies` 仍是 `^`），比上游更严格；两者 `lib/**` 逐字节相同，所以无功能差异。

## 11. 评估：OIDC 改成直接用 oauth2-proxy？

### 11.1 先纠正一个直觉：这不是"换掉 auth-oidc 的路由"，而是"fork 还需不需要存在"

`vendor/dsh-web-auth` 这个 fork 的**唯一目的**就是拿到一个"路由匹配之前的请求闸门"。
认证一旦移出进程，这个需求就消失了 —— 可以直接用官方 `dsh-host-webserver`。
所以两个方案是互斥的整套架构，不是同一套里换一个组件：

| | A. 现在的 in-process 闸门 | B. oauth2-proxy（sidecar / 独立 Deployment） |
|---|---|---|
| webserver | **fork**（+ 漂移守卫） | **官方包**，fork 删除 |
| OIDC 实现 | 自己维护（`packages/auth-oidc`，~822 行：discovery/JWKS/PKCE/session codec/login 页/gate） | oauth2-proxy |
| P1（`isLoopback`） | 需要 | **仍然需要**（与谁做认证无关） |
| P2（cookie 层） | 需要 | **仍然需要**（浏览器拿不到 launch token） |
| 身份如何进入平台 | 进程内验签的 session cookie（不可能伪造） | `X-Auth-Request-User/Groups` 头（**只有**在 DSH 不可绕过代理直连时才可信） |
| 闸门覆盖面 | 全部路由（含上游不管的 `/plugins`、`/plugins/events`） | 代理层面，天然全覆盖 |
| 网络前提 | 无（进程内） | DSH 必须只经代理可达；否则 P2 让裸端口等于全开放 |
| 失败模式 | 闸门未注册 → 已修为 **503 fail-closed**（见 §11.2） | 代理挂掉 → 502/503；DSH 不会裸奔（只要隔离成立） |

### 11.2 已经先修掉的一个真实缺陷：fork 原本是 fail-open

原实现是 `if (gate !== void 0 && !(await gate(req, res, "request"))) return;` ——
**没有注册闸门时，请求照常分发**。也就是说只要 `dsh-auth-oidc` 因为任何原因没激活
（配置校验失败、被临时 disable、apply 抛错），整个 Harness 就会**无认证地对内网开放**
（而上游的 `/plugins`、`/plugins/events` 本来就没有信任检查）。

已改成 deny-by-default：

* 请求路径：无闸门 → `503`，不分发；
* upgrade 路径：无闸门 → 直接 `socket.destroy()`（原来也是 fail-open 的）；
* 想要无闸门服务器就用官方 `@deepseek-ai/dsh-host-webserver`，fork 的语义就是"带认证的 webserver"。

已固化成断言（`smoke-web-trust.mjs`）：

```
ok  an un-gated fork refuses to serve (fail closed) — status=503
ok  registering a gate is what opens the seat        — status=200
```

这条修复**与选哪个方案无关**，但会显著影响选择：A 方案现在的失败模式是"不可用"而不是"裸奔"，
B 方案必须在网络层达到同等强度。

### 11.3 什么时候 B 明显更好

* **想删掉 fork**。这是目前唯一与官方**逐文件**耦合的地方，风险最高（虽然有漂移守卫）。
  换成 sidecar 后可以直接用官方 webserver。
* **不想自己维护 OIDC**。本仓库的 git 历史里已经有一条 `fix login JWKS rotation` —— 这类
  实现细节（JWKS 轮换、时钟偏差、PKCE、cookie 属性）是典型的"写一次、每季度踩一次"。
* **将来要做多用户**。oauth2-proxy 会给出**已验证的**用户/组头（`--set-xauthrequest`），
  平台只需要一个很小的"头 → `ctx.dshAuth`"桥；而 A 方案里我们已经有了
  `auth.currentUser(req)`，两者工作量相当，但代理侧还顺带给了 `--allowed-group`
  这种边缘侧粗粒度授权。

**在 k8s 里 B 的隔离要求是可以结构性满足的**：把 oauth2-proxy 作为 **同 pod sidecar**，
让 DSH 绑 `127.0.0.1`，Service 只暴露 sidecar 端口。这样 DSH 在集群里根本不可直连，
"信任代理头"就是安全的，而且顺带**不再需要 `host: '0.0.0.0'`**（回到上游威胁模型内，
官方拒绝 0.0.0.0 的那条顾虑也就不适用了）。

### 11.4 什么时候不值得换

* **B 并不减少补丁**：P1、P2 依然要在（见 §9.2/§9.3 的替代讨论）。把"认证位置"从进程内挪到
  sidecar，只换来"删掉 fork + 删掉 OIDC 实现"，代价是一个新容器 + 网络隔离约束 + 部署仓库改造
  （`dsh-platform-deploy` 要重做 ingress/Service/探针）。
* **多用户的核心问题它解决不了**：会话/设置/凭据仍然是进程级单例，审批广播仍然是全员
  （§10.7、§10.9）。代理给了身份，但 DSH 内部没有任何东西能消费它 —— 那部分工作照旧。
* **A 现在已经没有"裸奔"风险**（§11.2），而且闸门覆盖面比代理更"贴近"应用（同一进程、
  同一 fiber 生命周期）。

### 11.5 如果决定换，必须注意的四件事

1. **不能两套并存**。若保留 fork 又上代理，DSH 侧仍会要求它自己的进程内闸门；
   一旦忘记注册就是 503（fail-closed 会把错误变响，而不是静默降级）。
   迁移是"整套切换"：官方 webserver + 删 fork + 删 `auth-oidc` 的 gate/OIDC 部分。
2. **隔离必须成立**。P2 之后，任何绕过代理直连 DSH 端口的路径都等于完全访问。sidecar +
   `127.0.0.1` 是唯一"结构性"的做法；靠 NetworkPolicy 也行但属于策略而非结构。
3. **身份头必须只在隔离成立时被信任**，并且要显式剥掉客户端自带的同名头
   （oauth2-proxy 会覆盖，但要确认 `--set-xauthrequest` 与 `--reverse-proxy` 的组合，
   以及 `/api/remote.mux` 的 WebSocket 升级路径也带头）。
4. **长连接要专门调**：`/api/remote.mux`（WebSocket）与 `/plugins/events`（SSE）都是长连接，
   代理默认的缓冲/超时会打断它们（SSE 典型症状是事件被攒住不下发）。需要显式设置
   `--flush-interval`、读超时与 WebSocket 超时，并在冒烟里覆盖这两条路径。

### 11.6 具体到当前部署（dsh-platform-deploy）要改什么

现在的形状是：一个 Ingress → control-plane Service → DSH 单容器（fork webserver + 进程内 OIDC 闸门），
OIDC 参数走 chart values（`auth.oidcIssuer/oidcClientId/redirectUri/adminGroups` + 两个 secret ref）。
换成 sidecar 形态大致是：

1. control-plane Pod 增加 `oauth2-proxy` sidecar（`--provider=oidc --oidc-issuer-url=… --email-domain=*
   --upstream=http://127.0.0.1:3080 --set-xauthrequest --reverse-proxy=true --flush-interval=…`），
   cookie secret 用现有 secret 机制；
2. Service 的 `targetPort` 改成 sidecar 端口（4180），Ingress 不动；
3. DSH 侧 `docker/profiles/web.cordis.patch.yml`：把 `webserver` 的 `disabled: true` 与
   `webserver-gated` 的 insert 一起删掉（恢复官方 webserver 行，并回到 loopback 绑定）；
4. `scripts/patch-dsh.mjs` 的 P1/P2 **保留**；
5. `packages/auth-oidc`：删除 gate/OIDC/session 部分，若要多用户身份，只保留一个很小的
   "`X-Auth-Request-User/Groups` → `ctx.dshAuth`" 桥（并依赖第 2 条的隔离前提）；
6. 冒烟：把 `smoke-web-trust.mjs` 的"闸门"换成代理侧断言（未带代理会话 → 302/401，
   带会话 → 200，且 `/plugins`、`/api/remote.mux`、`/plugins/events` 都要覆盖）。

改造量集中在一个 chart + 一个 profile 文件，不大；真正的工作量在**验证长连接与隔离**。

### 11.7 建议

* **短期**：保持 A（现在已 fail-closed），把 §9.2 的 P1 换成官方 transport hook，
  并把 §10 的多用户缺口按优先级补上（审批定向 → 可见性过滤 → `user-domain` → `rbac`）。
  这些收益比换代理大得多，而且不被任何架构选择阻塞。
* **中期**：如果你更看重"不再维护 fork 和 OIDC 实现"，B 是合理的，**但请以 sidecar +
  loopback 的形式做**；那时顺手把 `host: '0.0.0.0'` 去掉，回到上游的威胁模型内。
* **无论选哪个**：向上游提 gate 座位这件事都值得做 —— 它让 A 方案彻底摆脱 fork；
  就算最终选 B，上游多一个中间件缝对所有人都是净收益。
